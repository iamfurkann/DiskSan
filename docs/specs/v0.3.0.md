# DiskSan v0.3.0 - Audited Read-only Native Capability Discovery

Status: DEVELOPMENT SPECIFICATION. This document authorizes implementation and safe tests, NOT public release or any destructive operation.

## 0. Authority, baseline and non-goals

The starting point is published v0.2.0 (`d00be042e9a64552b86b3fc807d2995e4110b165`), but Codex MUST first inspect the actual branch, HEAD, status and user edits. Treat newer repository state as authoritative. Consult `AGENTS.md`, `docs/BASELINE_0.2.0.md`, `docs/PROTOCOL_QUERY_AUDIT_0.3.0.md`, and the current source and tests. Implement coherent production functionality, not a documentation-only prototype.

Version 0.3.0 adds explicitly requested, narrowly scoped, real *read-only controller protocol information* queries to the preexisting inspection and capability evidence architecture. It is NOT a sanitization release. Do not add or execute erase, sanitize, discard, format, security unlock, firmware update, namespace management, device self-test start, feature mutation, reset, power-management transition, mount change, privilege escalation, or user-data sector access. Do not create a general-purpose native pass-through command framework exposed to users.

Scope is intentionally asymmetric: implement an independently audited Linux native NVMe Identify Controller pathway and, if demonstrably safe and supported, the equivalent Windows NVMe property-query pathway. Introduce clean transport/provider seams for ATA/SCSI/macOS but retain *unavailable/unknown* when an exact approved read-only mechanism cannot be established or reliably tested. A Linux-only validated provider is better than speculative cross-platform parity.

## 1. Definition of done and release posture

- Existing `list`, `info`, `assess`, `capabilities`, `--json`, schema-2 inventory/device fields, JSON escaping, nullable/unknown behavior, and exit classes remain stable.
- `capabilities <selector>` (without probing) remains metadata-only, with no native protocol commands and no new open/access requirements.
- Introduce only an explicit `capabilities <selector> --probe` opt-in. The same option is allowed before or after the selector with existing argument grammar, including `--` for literal selectors, with no ambiguous interpretation. Do NOT enable probing through environment variables, default settings, background tasks or `assess`.
- The opt-in path queries only audited, constant, bounded, read-only native request types, produces provenance, and leaves unproven dimensions unknown. It does not produce erase authority, a reusable target handle, or a future validity promise.
- Production native probing must be absent/declined on unsupported platforms, adapters or unsupported device types with a truthful reason, not with fabricated negative support.
- Every live request has deterministic synthetic positive and negative tests plus native request construction/flag allowlist tests; any real-device test is separately requested by the maintainer on a deliberate selected device.
- CMake compiles and tests the relevant platform modules with warnings as errors. On available hosts run full Release and sanitizer suites and package/document checks. All external platform/hardware skips are stated.
- Completion yields a candidate handoff with tested scope; git stage/commit/push/tag/release remain maintainer actions.

## 2. Existing architecture, extension points and invariants

Use existing `ds_assessment` check observations, `ds_cap_evidence` method/dimension/state/source/detail, and `ds_assessment_evaluate`. Six existing method families remain unchanged: NVMe block/crypto/overwrite, ATA security/sanitize and SCSI sanitize. Four dimensions remain independent: support, os_access, applicability and passthrough.

The existing `src/core/capabilities.c` provides native metadata-only unknowns for all 24 method/dimension combinations. Preserve this as the default; add a new opt-in provider entrypoint and result merger without changing unrelated discovery, usage, identity or output semantics. New code must support safe coexistence with the old provider: a successful probe must not be reduced to `unknown` by the old unconditional placeholders. Preferred approach: choose exactly one provider per operation (metadata-only vs audited-probe), and supply explicit unknowns for every dimension not established by that provider. Avoid contradictory duplicate evidence unless the underlying sources truly conflict.

Current `ds_assessment` has `DS_ASSESS_LIMIT=64` capacity *for all method observations*, not per method. With six methods and four dimensions that is only 24 baseline entries. Design additions to fit worst-case exact duplicates, independent sources and failures, or deliberately evolve the model/limit with bounded memory, allocator/stack analysis, compatibility tests and clear diagnostic behavior. Never truncate a result to claim success.

A source/transport API separates: (a) request-kind enum with only audited constants; (b) native request construction/handle lifecycle; (c) validated bounded response; (d) portable decode; (e) independently evidenced capability dimensions; (f) policy and JSON. Windows and Linux native structures must not enter portable public headers.

All probing occurs *within* the existing selected-target observation window, with revalidation afterward. A controller-wide query may outlive an individual namespace identity; explicitly check the association between the selected namespace and controller before and after where observable. Existing before/after selection is not atomic and cannot detect every ABA event. A controller scope mismatch or disappearing target is an invalid-target failure, not a successful probe.

## 3. Threat model and request construction

Threats: misdirected device path/alias, stale namespace/controller relationship, user-controlled native command parameters, shared controller affecting other namespaces, USB translation and false passthrough claims, altered/truncated kernel driver responses, unexpected native API privileges, malformed strings, signedness/length overflow, denial-of-service through huge or repeated requests, leaked handles, and sensitive firmware metadata in logs.

Allowed protocol data is read-only *controller/namespace metadata*, never storage user data. Every request begins from a zeroed fixed-width structure and sets a closed set of constants; command opcodes, CNS, log-page identifiers, data lengths, namespace identifiers, timeouts and pointers must not be provided by CLI users. Device paths themselves are selectors, not ioctl parameters. Validate selector, native role, protocol and identity before any request; reject unknown/bridge/virtual/aggregate topology until the precise path is demonstrated safe. Reject opening `/dev/nvme*` by guessing a controller number from a namespace string. Do not create or use a writable handle.

Make the set of permitted concrete native requests visible in code and in `docs/PROTOCOL_QUERY_AUDIT_0.3.0.md`. Audit each primitive against OS headers and vendor-independent docs before implementation. A query's *name* is not a safety proof; the request direction and exact subfunction matter. Negative fixtures assert forbidden request variants cannot be emitted.

Require hard upper bounds, initialized request and response buffers, exact minimum/maximum return size checks, safe offset arithmetic, endian-aware field parsing, reserved-field validation when defined, and no reliance on C packed-struct casts of untrusted memory. Avoid forwarding raw Identify buffers to JSON, stdout, logs or release artifacts. Parse only documented, stable fields relevant to capability findings. Sensitive controller text, raw device paths/serials, and machine inventories remain private by default.

## 4. Concrete scope of native provider v0.3.0

### 4.1 Linux NVMe (primary implementation)

Research exact Linux kernel UAPI and privilege semantics of `NVME_IOCTL_ADMIN_CMD`/`NVME_IOCTL_ADMIN64_CMD`, including behavior under read-only file descriptors and both namespace and controller character/block-device paths. The interface can submit *many dangerous admin commands*; it is NOT intrinsically read-only. If a safe request/path cannot be established for a given host, return unavailable and execute no command.

MUST implement in a small, auditable constructor a controller Identify command (`NVMe admin opcode 0x06; CNS Identify Controller = 0x01; 4096-byte controller data`) only when the exact mapping and privileges are verified. Hardcode opcode, CNS, zeroed unused dwords, metadata length zero, bounded data-in pointer, length 4096, and bounded timeout. Do not permit Set Features, Format NVM, Sanitize, Firmware Download/Commit, Security Send/Receive, Namespace Management, I/O commands, resets, or arbitrary Get Log Page variants. Under any access denial, do NOT retry with O_RDWR, sudo or alternative unsafe device nodes.

Namespace Identify (`CNS 0x00`) is an OPTIONAL separate audited entry conditioned on known NSID and a demonstrated safe OS handle mapping. A narrowly fixed Get Log Page query is also OPTIONAL and must receive its own individual allowlist audit, including log page ID, flags, scope, data length and driver permission. Prefer shipping controller Identify rather than enabling unreviewed log queries. No probe targets are selected automatically in CTest on developer hardware.

Parse vendor-independent Identify Controller byte ranges with explicit bounds and little-endian conversions. Map *only documented* capability indicators to the corresponding `support` field; distinguish sanitize command support flags from applicability to a selected namespace, platform access, USB passthrough or ability to execute a command. For any ambiguous bit/command-set/profile/version, report unknown. Even when hardware support is positively observed, the other dimensions remain independent and no operation is authorized.

### 4.2 Windows NVMe (secondary implementation)

Use the documented `IOCTL_STORAGE_QUERY_PROPERTY` with a validated `STORAGE_PROPERTY_QUERY` and `STORAGE_PROTOCOL_SPECIFIC_DATA` for a narrowly fixed `NVMeDataTypeIdentify` controller request. Do not use general `IOCTL_STORAGE_PROTOCOL_COMMAND`, `IOCTL_SCSI_PASS_THROUGH*`, vendor-specific commands or storage property Set requests. Retain existing read/zero-access behavior and explicitly audit the access mask on the selected device handle. Check actual Windows SDK/OS version availability and the full returned `STORAGE_PROTOCOL_DATA_DESCRIPTOR` layout, size, protocol, offset and length before decoding.

MSVC native build and deterministic fake-DeviceIoControl fixtures are required to claim implementation. The hosted Windows runner's `windows_integration` passing with an empty/no NVMe disk list is NOT physical protocol validation. If native API behavior is unavailable or cannot be safety-verified, compile a well-defined unavailable adapter and record an external acceptance gate instead of enabling an unsafe alternate path.

### 4.3 macOS, ATA, SCSI and USB bridges

Do not repurpose Disk Arbitration/IOMedia observation into a claimed NVMe protocol query. For macOS, name the exact supported public framework or documented system interface and verify access, side effects and typed reply handling before adding any live query; otherwise `unavailable` with a reason is correct.

For ATA and SCSI, establish concrete read-only IDENTIFY DEVICE / INQUIRY or VPD query contracts and per-OS access requirements before enabling native calls. Since data-out directions, SG_IO/ATA pass-through families and USB bridge transformations can support state-changing commands, generic pass-through is prohibited. Implement parsers and synthetic fixtures where useful, but never claim hardware-probe coverage until a safe native provider is demonstrated.

An observed USB transport is NOT proof of NVMe/ATA passthrough. Do not attempt bridge-specific or vendor commands. For unknown or layered controllers, all method/applicability/passthrough dimensions remain unknown. Not supported vs not accessible vs not checked must be unambiguous.

## 5. CLI and JSON contract

New syntax:

```
disksan capabilities [--json] [--probe] [--] <native-device-selector> [--json] [--probe]
```

`--probe` is invalid with `list`, `info`, and `assess`; reject with usage exit 2 and do not perform discovery. Existing standard `capabilities` remains byte/semantics compatible for existing fixtures (apart from project `version` after bump). The opt-in path uses the *existing* schema-2 assessment envelope, `operation=capabilities` and retains existing `device`, identity and findings data. Only additive fields may be introduced, such as `probe` (requested/performed/status/reason/provider), strictly documented and tested. New unknown-safe source evidence should generally be carried by existing method `evidence` elements with stable source names. Do not change existing nullability, exit class, string escaping or method ordering.

Define a stable reported distinction between: (a) not requested; (b) requested but unavailable; (c) attempted and hardware returned a valid supported/unsupported indicator; (d) partial/malformed response; (e) target changed. If the inspection completes with an unavailable optional provider, retain an explanatory `unavailable` result; a mandatory query safety or identity violation returns a nonzero exit without a success payload. Do not silently pretend a device has no methods.

Maintain exact `erase_authorized:false`, `identity.guarantees_future_identity:false`, `identity.atomic:false`, and `identity.valid_until:"end_of_observation"`; probing must not upgrade identity confidence merely because a request succeeded. Exit 0 means inspection completed, even when `inspection_status` is blocked/review_required; a successful process exit is not an erase permission. Output errors fail nonzero. Omit raw response bodies and private identifiers from debug/default log messages.

## 6. Portable decoders and evidence semantics

- Write pure buffer decoders, with named offsets, lengths, fixed endian functions, and explicit version guards. Keep C17 overflow checks, no undefined shifts and no unaligned pointer reinterpretation.
- Test known static positive/negative fixtures for controller capabilities, missing options, unknown bytes, truncated 0..4095 lengths, wrong protocol/metadata, contradictory reports, NSID/path mismatch, unrecognized controller versions, and all unsupported request variants.
- Report supported or unsupported ONLY from a correctly parsed, scope-matched authoritative field. Some optional command families may be unsupported while others are unknown; do not correlate unrelated flags.
- On permission error: keep `os_access` as unavailable (or unknown according to documented dimension taxonomy), not method unsupported. On no valid protocol response: keep method support unknown. `passthrough` remains unknown unless directly and safely established, not simply true because a request returned data.
- If a chosen method lacks a normative field in Identify Controller, leave it unknown. Do not infer physical erase guarantees, cryptographic key destruction outcomes, drive health, NIST compliance, or a success certificate from advertised support bits.
- Source paths indicate exactly which API or fixed controller field supports each claim. Fixed-size evidence array overflows fail closed rather than truncate.

## 7. Resource safety and cross-platform behavior

Ensure every file descriptor/HANDLE and temporary buffer is closed/freed on success and every early failure; no use-after-close or borrowed native pointer escapes. Run existing allocation/identity fault suites unchanged plus new response/permission/request failure injection. No dynamic library or shell invocation required solely to probe devices. Do not add `nvme-cli`, `smartctl`, `diskutil`, `lsblk`, PowerShell or shell-outs in production.

Preserve Windows `wmain` UTF-16 behavior and both terminal-safe and valid UTF-8 JSON encoders. Invalid selectors (ordinary files, directories, inaccessible endpoints, false symlink aliases) fail before any protocol command. The probe must never be automatically retried using another alias that could refer to a different controller. Bound timeouts and the number of commands to a small documented constant; no endless retries, loops or background watchers.

## 8. Required test matrix

| Test area | Minimum objective |
| --- | --- |
| Portable decoder | Exact byte offsets/endian/version flags; valid, invalid, short/long, malformed and randomized fixed-byte buffers |
| Policy semantics | All six methods x four independent dimensions; support vs access vs applicability vs passthrough, conflicts, unknown and unavailable |
| CLI gating | `capabilities` remains non-probing by default; only explicit legal `--probe` invokes provider; invalid forms invoke zero native commands |
| Native safety | Fixed opcode/selector/buffer/flags and exact allowlist; no write flags, data-out, mutation/reset/format/sanitize, elevation or arbitrary pass-through |
| Failure paths | Permission denied, missing capability, short response, errno/driver status, target disappears, controller changes, buffer/alloc and output failure |
| Platform | Linux native GCC/Clang+ASan/UBSan where reachable; macOS AppleClang; Windows native MSVC+fault fixtures and available integration |
| Compatibility | Existing all core/discovery/assessment/CLI/JSON tests unchanged; schema-2 device fields and exit classes preserved |
| Distribution | Docs/manifest, package exact bytes and output, version/help, release SHA checks after the final source revision |

Synthetic command tests do not prove physical hardware behavior. A real test must be opt-in, manually selected, non-system device, non-elevated by default, with recorded controller/transport limitations and no raw serial disclosure in shared logs. Do not skip real-hardware gates by renaming them as portable tests.

## 9. Milestone sequence

M0: baseline and protocol API research. M1: portable decoder and evidence semantics. M2: exact native request allowlist and negative safety fixtures. M3: opt-in CLI, JSON and target-window integration. M4: Linux NVMe Identify Controller provider. M5: Windows property-query provider and optional audited platforms/protocols, else explicit unavailable stubs. M6: native faults, regressions, sanitizers, compatibility. M7: documentation, CI/source review, owner hardware acceptance checklist and release candidate handoff.

Update `docs/PROGRESS_0.3.0.md` after each verified milestone, not after every command. Include source revision, exact test commands/results, limitations and next action. No git stage/commit/push/tag/Release without maintainer authorization.

## 10. Release gates

A 0.3.0 candidate requires (1) a verified closed read-only query audit; (2) no non-allowlisted command in production or test run against real hardware; (3) portable/available native tests and sanitizers passing; (4) compiled Windows/MSVC and actual CI evidence or a visibly declared preview limitation; (5) complete schema and CLI documentation; (6) manifest/checker and packaging; (7) owner-confirmed physical-device acceptance before claiming physical support. A platform's unavailable provider can ship if limitations are explicit. Historical tag CI cannot count as v0.3.0 validation.

`v1.0.0` is a separately gated future full-product stable milestone; 0.3.0 must not make destructive promises in advance.
