# DiskSan v0.4.0 - Inspection-only Planning, Simulation and Desktop Prototype

Status: DEVELOPMENT SPECIFICATION; no 0.4.0 code is claimed to exist. Base: published 0.3.0 at `02beaae641228864af161a17563a01d62850ad6b` as researched on 2026-10-28. Read AGENTS.md first.

## 1. Product objective and non-goals

Add a genuinely useful, conservatively modeled **non-executable inspection plan** and **simulation transcript** for a selected storage device, plus an optional working Qt 6 Quick/QML **read-only desktop alpha**. Keep standalone C17 CLI behavior and existing binary packages working without any Qt dependencies. Prioritize evidence, comprehensible risk explanation and operator trust over decorative UI.

This version must **not** submit a sanitize/erase/format/discard command, read or write user-data sectors, mount/unmount a filesystem, escalate privilege, produce an erasure certificate, or add a callable future execution backend. No real disk manipulation is justified by the word "simulation". Avoid UI elements labeled "Erase", "Run Sanitization", "Start Wipe" or identical. A hypothetical plan is not authorization and cannot be persisted as an authorization credential.

## 2. Existing contractual boundaries

- Do not regress 0.3.0 `list`, `list --all`, `info`, `assess`, `capabilities`, `capabilities --probe`, default metadata-only behavior, JSON schema 2 device records, unknown semantics or exit classes 0..4.
- Keep the sole enabled native protocol query fixed to its previously audited opt-in path. `plan`, `simulate`, UI refresh and UI assessment **must never invoke** `--probe` automatically or issue any native protocol query.
- All new paths use native read-only target discovery/assessment with before/after identity checks; no extra mutable device access.
- A success exit code indicates only successful **inspection or simulation generation**, even if content contains blockers; no success code is an operation outcome.

## 3. Portable plan model

Create a small C17 portable `ds_plan` model with bounded evidence, constraints and deterministic step definitions. Suggested files: `include/disksan/plan.h`, `src/core/plan.c`, `src/output/plan_output.c`; adjust naming only to match actual repo conventions. The portable model performs no OS calls, accepts a successfully evaluated 0.3.0 assessment and a selected device snapshot as borrowed input, and returns an owned diagnosis.

Represent these independent concepts without collapsing them: `target_observed`, `identity_confidence`, `usage_status`, `topology_coverage`, `method_evidence`, `privilege_unknown`, `physical_scope_unknown`, `execution_unavailable`, `verification_unavailable`, and `policy_blockers`.

For each finding retain a stable code, severity, evidence/scope pointer and human explanation. Do not materialize a "sanitization target" from a serial, user-supplied friendly label, default device index or prior JSON. Current device identity may be described, never authorized.

Suggested state vocabulary: `blocked`, `review_required`, `insufficient_evidence`, `inspection_only`. No `ready_to_erase` state in 0.4.0. A drive with zero known blockers still needs unresolved future authorization, exclusively locked scope and completion verification; therefore it remains non-executable.

## 4. CLI entry points

Proposed (additive) exact command grammar:

```
disksan plan [--json] [--] <native-device-selector> [--json]
disksan simulate [--json] [--] <native-device-selector> [--json]
```

These use the same safe selector resolution as `assess`. Reject missing, duplicated, malformed options, ordinary files and stale devices using existing exit codes and no success JSON. Literal `--` ends option recognition: if supplied, all options including `--json` must precede it. Do not accept `--method`, `--force`, `--execute`, raw opcodes, sector ranges, `--probe`, `--yes`, `--sudo` or arbitrary commands in these two verbs. No promise of a later executable analog that accepts the same plan arguments.

`plan` reports hypothetical prerequisites, **observed** risks and unverified requirements. `simulate` derives a bounded deterministic **dry-run transcript** from the same facts; it must not sleep, perform an operation, open user data or claim any media result. A simulated stage may show `would_block`, `unknown_requires_review`, `not_implemented` or `inspection_step_modeled`. It cannot show `erase_started`, `erase_complete`, `verified` or other operative terms without the qualifier that it is only a fixture simulation.

## 5. JSON contract (schema 2, additive distinct operation envelope)

Keep a separate `operation` value `plan` or `simulate`. Required top-level fields: `schema_version:2`, `application:"DiskSan"`, `version`, `operation`, `mode:"read-only"`, `device` (unchanged schema-2 single device record), `inspection_status`, `simulation_only:true`, `execution_available:false`, `erase_authorized:false`, `identity` with `atomic:false`, `guarantees_future_identity:false`, `valid_until:"end_of_observation"`, `findings`, `prerequisites`, and `steps` (empty or absent for plan if explicitly documented). Use bounded strings and stable codes, no raw memory addresses, no serial duplication in logs, no disk metadata fabrication.

A `simulate` response must contain `simulation_result:"non_executable_model_only"` and no completion/verification/effect claim. States must preserve uncertainty; unsupported/unknown/unavailable native capability remain distinct. Explicitly distinguish live device observations from model-derived hypothetical steps and synthetic fixture data. Exhausted output/allocations: fail safely, no success payload on internal fatal error (partially written stream may remain; consumer must validate exit code and complete JSON).

## 6. Threat/authorization architecture (design-only)

Document in `docs/THREAT_MODEL_0.4.0.md` the trusted identities and untrusted surfaces, TOCTOU/ABA and hotplug, system/boot/swap/RAID/APFS dependencies, controller-vs-namespace scope, USB passthrough, concurrent consumers, user confusion, privilege boundary, hardware failure/power-loss/recovery and false-success reporting. Design hypothetical authorization as an independent future service; do not expose that service as a library function or executable in 0.4.0. Document that typed confirmation alone, old assessment JSON, CLI exit 0, UI button, or capacity/serial match cannot authorize erasure.

## 7. Desktop alpha - Qt 6 Quick/QML, optional

Implement a minimal but **working** standalone `disksan-desktop` when Qt 6 Core/Quick/Qml/QuickControls2 are available. Use CMake option `DISKSAN_BUILD_DESKTOP=OFF` default; if explicitly ON and dependencies are missing, fail clearly rather than silently pretending to build. C CLI must build unchanged when Qt absent. Build C++ bridge and QML only inside `desktop/`, with no Qt classes in portable public C headers.

Required read-only user journeys:
1. App starts to a safe empty state (no false "all devices safe" claim).
2. Explicit Refresh lists observed disks through **known** DiskSan CLI binary and `list --all --json`; show role, model/path, reported capacity, OS and unknown values faithfully.
3. Selecting a device loads `info`, `assess` and metadata-only `capabilities`; display evidence, policy blockers and unknown states without inventing device capabilities.
4. User can request a **simulation preview**; show `plan` and `simulate` output with permanent "SIMULATION ONLY - DOES NOT ERASE DATA" messaging.
5. Handle unavailable CLI, denied permissions, invalid JSON, no devices, stale selections, concurrent refresh, timeout, too-large output, and app shutdown without UI freezes.

Never include a real or mock "Erase Now" control. No automatic `--probe`. A separate **clearly labeled DEMO DATA** fixture mode is allowed for screenshots/tests only and must never be confused with real inventory.

Recommended integration: `QProcess` with the **absolute configured executable path**, fixed enumerated subcommands and separately passed argument strings (no shell, `startCommand`, command string concatenation, PATH lookup, or external scripts). Validate version/schema, exit status, JSON types, record limits and child output sizes before showing as live facts. At each update clear old data or mark it stale; response order must not override newer selections. Avoid echoing private serials or raw JSON in telemetry/logs. See `docs/GUI_ARCHITECTURE_0.4.0.md`.

Qt 6 minor versions change OS deployment minima. Document the exact tested Qt version and desktop OS matrix, not inherited CLI minimums. Review LGPLv3/GPL/commercial obligations of used Qt modules, dynamic-link deployment and required attribution; no blanket license compatibility assertions.

## 8. Verification and required negative cases

Use `docs/TEST_MATRIX_0.4.0.md`. At minimum implement portable plan policy truth-table tests, CLI option/JSON/errors/stream failure tests, fixed simulation transcript tests, no-side-effect checks with substitute native adapters and a fixture that **fails immediately** on accidental native protocol query or destructive call. Existing 0.3.0 old-default CLI and `--probe` specific tests must continue to pass. Qt GUI tests: provide synthetic CLI fixture, JSON parser tests, QProcess argument allowlist checks and QML smoke/offscreen tests where supported. Do not treat a displayless runner skip as UI PASS. For real Mac/Linux/Windows, run only normal read-only inspection tests (not automatic physical NVMe probes). Hardware may be used only when the operator deliberately authorizes a separately audited observational acceptance.

## 9. Platform, packaging and backward compatibility

- Linux GCC Release + Clang ASan/UBSan, macOS AppleClang, Windows MSVC C17 test sets remain release gates at accessible CI runners. Add desktop optional jobs explicitly if the CI runner can install the exact Qt version; avoid making unrelated CLI builds depend on GUI SDKs.
- Source remains Apache-2.0; separately document Qt module licenses. If the UI cannot be built or tested on a platform, mark that exact UI target preview/NOT_RUN rather than making all-three-platform GUI claims.
- Existing CLI archives and metadata must remain valid without Qt. Desktop packaging is **optional alpha** and must not be silently bundled in current CPack artifacts. GUI deliverable can be source-build only in 0.4.0 if signed deployable assets are not validated.
- Update `README.md`, `docs/DEVICE_MODEL.md`, `docs/ARCHITECTURE.md`, `docs/TESTING.md`, `docs/ROADMAP.md`, `SECURITY.md`, `CHANGELOG.md`, `CMakeLists.txt`, `docs/FILE_MANIFEST.txt` for actually implemented behavior only. Do not copy prewritten docs as proof of completed work.

## 10. Milestones and completion

M1: portable plan model, stable conservative policy, detailed threat model.
M2: inspection-only `plan` CLI/JSON and negative/error tests.
M3: simulation transcript/CLI, deterministic fixtures and side-effect guards.
M4: optional Qt desktop architecture + working device inventory/selection/assessment and robust native-process bridge.
M5: optional Qt desktop plan/simulation views, accessibility, empty/error/unknown and demo-data handling.
M6: cross-platform C CLI regression, sanitizer/fault coverage and optional GUI build/smoke where tools exist; documentation/manifest/package validation.
M7: evidence-based 0.4.0 handoff, known limitations, release candidate notes and explicit external gates.

No completed milestone is inferred from this spec. Implementation-complete does not imply release-ready, public GUI binaries or safe erasure. Release publication requires maintainer authorization.
