# DiskSan v0.2.0 - Target Assessment, Policy and Read-only Capability Evidence

**Status:** Implementation specification for Codex. **Baseline:** source v0.1.1 (see `docs/BASELINE_0.1.1.md`). **Primary requirement:** remain a non-destructive disk inspection utility.

## 1. Outcome

Deliver an evidence-based, read-only preflight subsystem that can describe a selected storage target, explain its observed usage/topology hazards, and report what sanitization-related capabilities are *observed*, *unknown*, or *unavailable to inspect* without attempting sanitization. Its decisions must degrade conservatively across Linux, macOS, and Windows. Existing commands must remain compatible.

A successful v0.2.0 implementation **does not** make a disk safe to erase, does not authorize erasure, and does not assert completion of any destructive operation. Its outputs are observational assessments for a hypothetical future operation.

## 2. Hard requirements and exclusions

### Required

- Revalidate user-selected target identity, role, topology, generation and relevant state as closely as the accessible native APIs permit; clearly expose non-atomicity and missing guarantees.
- Separate *observed facts* from *derived policy findings* from *protocol capability evidence*.
- Present machine-readable explanatory findings with stable codes, provenance/evidence, severity and uncertainty; unknown is never silently converted into safe or supported.
- Detect observable blockers such as partition/logical layer vs physical target, mounts/in-use consumers, active swap, holders/slaves, system/boot/storage-layer dependencies when reliably observable; otherwise emit an `UNKNOWN` finding and explain the unverified dimension.
- Report platform/API limitations truthfully; local read-only tests and synthetic fixtures must not be confused with physical controller verification.
- Preserve v0.1.1 inventory and JSON schema-2 compatibility and the current read-only operating envelope; add fields/commands in a documented and testable way.
- Use deliberate, maintainable APIs, bounded allocations/strings, ownership contracts, deterministic output and comprehensive negative tests.

### Out of scope for v0.2.0

- Issuing NVMe Sanitize or Format NVM, ATA Secure Erase/Sanitize, SCSI SANITIZE, crypto erase, TRIM/discard, wipe, partition modifications, filesystem mutation, mount/unmount, key destruction, firmware update, repair or data-area read/write.
- Generating certificates of erasure, assigning NIST Clear/Purge outcomes, or claiming physical erasure capability from model strings, USB bus type, `rotational=0`, advertised marketing features, or an unsupported controller path.
- Implementing an erase confirmation dialog or unattended destructive flow. The feature must have no path that writes block data or invokes a destructive command.
- Treating administrative/root privileges as proof of device capability. Do not gain elevation merely to make a hardware test succeed.

## 3. Logical architecture

Retain the existing native discovery interface. Introduce cohesive modules/interfaces along these lines, adjusting names where integration benefits justify it:

```
CLI (list, info, assess, capabilities)
  -> device discovery (existing)
  -> target resolver / identity revalidation (new)
  -> topology & usage observations (OS-specific)
  -> pure policy evaluator (portable, deterministic)
  -> optional read-only protocol capability collectors (OS-specific, explicit allowlist)
  -> JSON/text output (schema/version policy)
```

Recommended boundaries:

- `target assessment`: takes a resolved snapshot record plus a fresh native observation, returns identity status and evidence, not an authorized write handle.
- `usage observations`: typed claims such as mounted, swap, boot/system, holder/slave, inaccessible/unsupported, with `TRUE`, `FALSE`, or `UNKNOWN` and source/limitation; a failed observation is not a false observation.
- `policy`: pure function over observations; no syscalls or direct OS privileges. Distinguish `BLOCKED`, `REVIEW_REQUIRED`, `NOT_EVALUATED` and a positive **inspection-only** state where supported; never issue `ERASE_AUTHORIZED`.
- `capabilities`: independent method-level states `OBSERVED_SUPPORTED`, `OBSERVED_UNSUPPORTED`, `UNKNOWN`, `UNAVAILABLE`, and precise provenance/limitations. Treat permission, bridge passthrough and command applicability independently.
- `rendering`: no terminal control injection; JSON exact numbers/null semantics; stable severity and warning codes.

If the existing data model offers a simpler approach, Codex may design a different internal layout, but the separation and observable behavior must remain intact. Do not implement needless frameworks.

## 4. CLI contract

Preserve all old commands. Add one cohesive, explicit read-only assessment surface, preferably:

```
disksan assess [--json] [--] <native-device-selector>
disksan capabilities [--json] [--] <native-device-selector>
```

Alternatives (e.g., one `inspect` subcommand with sections) are acceptable **only if** they reduce duplicated machinery without making semantics ambiguous; document final commands and test them. Never add an `erase` action in v0.2.0.

A `list --all` record is *not* an implicitly approved sanitization target. A selected partition, APFS volume/snapshot, RAID mapper, or USB-exposed logical target may be inspectable while its physical erase suitability remains blocked/unknown.

- Exit 0: inspection succeeded and returned an assessment, even if findings include blockers or unknowns. Distinguish content status from process success.
- Preserve existing nonzero exit classes for invalid usage/system/missing target/permission; a target changing during resolution must be a clear nonzero failure, with no partial success JSON.
- Do not leak device serials or raw inventories in logs, fixtures or CI artifacts; CLI itself may display observed metadata as designed.
- Support `--help`, `--version`, `--` option termination, JSON ordering/stability, UTF-8, and stdout write-failure handling.
- Document new additions as additive JSON fields and/or a new operation-specific JSON envelope, retaining the existing schema-2 fields for `list` and `info`. Decide if a `schema_version` bump is truly necessary and write compatibility tests before doing it. Avoid breaking downstream clients unnecessarily.

Suggested assessment payload (illustrative, not mandatory property names):

```json
{
  "schema_version": 2,
  "application": "DiskSan",
  "version": "0.2.0",
  "mode": "read-only",
  "assessment_kind": "target-preflight",
  "device": { "device_id": "synthetic-only" },
  "identity": { "status": "verified_for_snapshot", "guarantees_future_identity": false },
  "findings": [
    {
      "code": "usage_state_unverified",
      "severity": "review",
      "state": "unknown",
      "source": "synthetic_fixture",
      "message": "Usage cannot be completely established"
    }
  ],
  "inspection_status": "review_required",
  "erase_authorized": false
}
```

Real output must reflect actual evidence and may use a more coherent schema. The illustrative values are not live-device evidence. In particular, `identity` should not claim a durable physical guarantee.

## 5. Target identity and time-of-check/time-of-use

### Identity scope

- Identity inputs differ by platform and may include current native device path, major/minor, sysfs generation (`diskseq` where available), IOKit registry entry ID, Windows interface/device number and available verified IDs. Do not assume WWN, serial, path or size is globally unique or immutable.
- Resolve and check native node type and relationships before inspection. For Linux, preserve symlink/by-id handling; reject regular files and replaced nodes; use existing diskseq/devnum semantics where available.
- Read observations through a bounded time window; re-check identity at the end and report snapshot non-atomicity. If the device changed, do not return a misleading successful assessment.
- Never persist a token intended to authorize a future destructive operation. If a snapshot/fingerprint is exported, document it as *diagnostic, non-authoritative* and make it expire logically at the end of the observation.

### Ambiguity

- Explicitly surface removed devices, duplicate IDs, changed generation, unsupported topology, bridge indirection, and privilege restrictions.
- If kernel/OS data cannot demonstrate exclusivity or current identity, report unknown/review-required, not physical-safety success.
- Physical whole-device resolution must account for controller/namespace distinctions and storage stacks; a partition's parent link is not equivalent to an authorized physical target.

## 6. Usage and topology assessment

### Linux minimum

- Build a read-only view of relevant sysfs graph: `holders`, `slaves`, partitions, DM/MD/multipath/loop/virtual mapping and backing relationships as observed.
- Parse `/proc/self/mountinfo` and `/proc/swaps` defensively, including escaped paths and mount namespace caveats. Compare block identifiers, not merely brittle string names. A mount namespace may not represent host-wide usage; explicitly report limits.
- Detect accessible root/system mount and active swap involvement, including selected disk's ancestor/descendant relationships where reliable. Do **not** infer no uses because `/proc/self/mountinfo` lacks a record or a physical device appears writable.
- Make snapshots best-effort but explain missing system metadata and inaccessible topology. Missing data must not silently imply safe.
- Avoid mount, unmount, write-based lock probes, filesystem checks with side effects, shell pipelines with destructive commands, and reading block data.

### macOS minimum

- Use IOKit/Disk Arbitration read-only information to report observable volume/container/snapshot/mount relationships and system volume/boot uncertainty. APFS sharing, sealed system/data volumes, Fusion/RAID, and multi-device containers require explicit unknown if not fully resolved.
- No `diskutil` mutation. `diskutil` read-only reference commands may be used in tests if they are clearly non-destructive and safe.

### Windows minimum

- Use available read-only SetupAPI/storage/volume access metadata to describe observed volumes/partitions/system or boot usage. Do not assume `PhysicalDriveN` implies an idle physical device or a single sanitization namespace.
- If access restrictions or missing Windows test hardware limit observations, keep findings unknown and document the limitations. Native Windows tests are required before Windows is declared validated for the new feature.

### Platform parity

All platforms should produce structurally comparable assessment results. It is acceptable for a platform to return richer evidence on Linux and honest `unknown` findings elsewhere. **Never fabricate parity by guessing device support.**

## 7. Sanitization-related capabilities: strictly informational

- Separate device protocol/bus classification from actual method capability and from OS command accessibility. A SATA/NVMe/USB label is not proof of sanitize support.
- Prefer existing metadata for a baseline classification and add read-only **identify/log** queries only if they are explicitly reviewed and isolated behind a safe command allowlist with documented side effects, bounds and privilege behavior. A query may be observational while still requiring an OS control interface; audit each new request.
- NVMe: where safe and available, identify relevant controller/namespace features and sanitized-command capability flags and distinguish them from accessible/usable method support. Do not assume device-advertised SANICAP alone makes an operation executable or sufficient for a policy.
- ATA/SCSI and USB bridges: require independently validated identify/capability evidence. Through a USB bridge, SCSI command transport may obscure ATA/NVMe features; report passthrough `unknown` if not validated.
- Unknown and permission-limited devices must continue to be inspectable and must not cause fabricated capability values.
- Optional protocol-probe dependencies may be used only when their license, availability, minimum versions and deployment burden are justified. Prefer clean capability-provider seams so future 0.3.x backends can implement actual operations separately.
- Do not expose API methods callable as a destructive backend in 0.2.0. Capability data is informational only.

## 8. Portable policy rules and severity

Define a simple stable finding taxonomy. Suggested categories: `identity`, `role`, `usage`, `topology`, `capability`, `platform_limit`, `observation_error`.

- Explicitly observed active system/boot/swap/mounted dependencies, inappropriate logical target role for whole-media actions, or confirmed contradictory identity are blocking findings for *hypothetical future destructive suitability*.
- Incomplete ancestry/topology, unverified mount namespace, missing generation, unknown controller/bridge, incomplete physical-device evidence or unknown capability imply review-required/unknown.
- A target with no currently observed blockers may be described as `no_blockers_observed_in_snapshot` only if that wording is clearly *not* a safety guarantee.
- The policy engine must not output a yes/no authorization bit that could later be reused to bypass destructive preflight. An optional `erase_authorized` output must be the literal `false` for this version, but omission may be safer.
- Make diagnostics actionable but not alarming for routine unknown metadata. Keep policy machine-readable, deterministic and reviewable.

## 9. Security, reliability and compatibility

- Treat native metadata as untrusted. Validate lengths, overflow, ownership, allocation paths, integer conversions, UTF-8 and Windows UTF-16. Preserve warning provenance and sources.
- Keep OS-specific headers and protocol APIs out of the portable core; require explicit cleanup contracts and avoid leaking handles or memory on partial failure.
- Every new OS-level query gets: exact name, documentation link, required access, side-effect analysis, privilege behavior, fallback, tests and a justification for inclusion.
- Do not allow a partial scan to become a successful empty inventory. Preserve v0.1.1 ambiguity semantics (no silent deduplication on dev_t alone).
- No new runtime requirement on a platform without documenting package/library linkage and native-acceptance consequences.
- Do not hardcode owner workstation paths; use current local project paths and portable CMake configuration.
- Keep all maintained repository prose in English with Doxygen briefs as specified by `docs/CODING_STANDARD.md`; update `docs/FILE_MANIFEST.txt` whenever files are added/removed.

## 10. Validation and reproducibility

Required automated testing coverage includes:

1. Pure policy evaluator fixtures: mounted disk, root ancestor, active swap, read-only device, whole disk, partition, APFS volume/snapshot, loop/DM/MD/multipath, NVMe namespace, USB bridge, unknown usage/topology, permission-denied probes and conflicting evidence.
2. Target resolver: invalid selector, regular file, symlink, stale device number, changed generation/identity, hotplug race injected between observation steps, duplicate native ID, unknown/partial identity, unavailable parent.
3. Usage parser: mountinfo escaped characters, malformed numeric fields, repeated mount points, namespace caveat, swap parser boundaries, huge lines, no mounts, permission failures.
4. Capability providers: `unknown`, `observed_supported`, `observed_unsupported`, API unavailable and permission denied; USB bridge passthrough uncertainty; flag contradictions; no command that can alter any device.
5. Memory/error: failure injection on newly allocated objects, partial cleanup, repeated free, stable sorting, buffer limits, stream output failure, JSON UTF-8/large `uint64`, stale/duplicate evidence and malformed native responses.
6. CLI regression: all v0.1.1 commands and exit codes; new subcommand help, JSON schema, invalid options, changed device, no stdout success on fatal errors.
7. Platform validation: Linux native + VM as available; macOS real host; Windows MSVC native and CLI only if a Windows runner or owner's Windows machine is actually accessible. Unsupported/untested platforms must be reported explicitly.
8. Static/sanitizer: run available GCC/Clang warnings-as-errors, ASan/UBSan and existing package/documentation gates. Do not claim sanitizers that the runner does not support.
9. Read-only trace/review: prove newly used operations have no disk data writes, destructive ioctls, mounting changes, firmware commands or privilege escalation. Synthetic fixtures may write normal temporary files only.
10. Negative tests: partial observations must never produce `erase_authorized=true` or a success state implying erasure can proceed.

The following minimum project tests already exist; keep them passing and add focused tests instead of replacing them: `core`, `identity_faults`, `windows_metadata`, `output_contract`, `cli`, plus Linux native fault/integration tests, macOS integration, and packaging/documentation checks.

## 11. Suggested incremental implementation milestones

| ID | Deliverable | Exit criterion |
| --- | --- | --- |
| M0 | Current-checkout baseline, risk inventory, API and safety design | Initial build/test and accurate progress report; design makes no false authorizations |
| M1 | Portable target/usage/capability result models and policy engine | Typed unknowns, ownership, stable findings and deterministic pure fixture tests |
| M2 | Linux read-only target revalidation and usage graph | Mount/swap/holders/slaves/system dependency fixtures; change detection; native Linux tests |
| M3 | macOS and Windows native read-only assess adapters | Honest platform-specific availability; native tests where accessible; otherwise explicit blockers |
| M4 | Capability evidence collectors | Observations independently substantiated or `unknown`; no mutate-capable commands; test proof |
| M5 | CLI, JSON and text output integration | Backward-compatible old commands and new tested assessment surface |
| M6 | Fault injection, sanitizers, CI, docs and package checks | Relevant tests pass; unrun host gates recorded, not hidden |
| M7 | v0.2.0 candidate review and release handoff | Traceable matrix, remaining risks, source version, owner-only publication steps |

These milestones may be reordered or grouped if dependency analysis justifies it. Avoid phase-by-phase approval requests for routine engineering work; implement what is achievable safely, verify, log and continue. Do not increase token cost by repeatedly rereading the entire specification after every small change.

## 12. Definition of done

A candidate can be marked **IMPLEMENTATION_COMPLETE** only when:

- All reachable spec acceptance conditions are checked against code and tests, with no unresolved critical safety/identity regression.
- New CLI behavior is documented; v0.1.1 commands and schema behavior remain valid or documented compatibility changes have dedicated tests.
- Read-only guarantees are audited and no destructive path is present.
- Available Linux/macOS/Windows tests, sanitizers and CI are executed and their result URLs/commands accurately recorded; inaccessible hardware gates marked `BLOCKED/NOT_RUN` and not characterized as passing.
- `docs/PROGRESS.md`, `docs/ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/DEVICE_MODEL.md`, `docs/TESTING.md`, `README.md`, `CHANGELOG.md`, `SECURITY.md` (if relevant), release notes and source manifest reflect reality.
- An owner-facing summary includes: changed files, important design decisions, evidence per platform, known unresolved issues, package/release readiness, and exact suggested manual acceptance steps.

A separate status **READY_TO_PUBLISH** requires maintainer review and any release gates the maintainer chooses. A Codex goal must not conflate implementation completion with GitHub publication. Codex must never claim external native testing occurred solely because a workflow exists.
